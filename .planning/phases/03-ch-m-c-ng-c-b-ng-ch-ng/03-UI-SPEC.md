## Spacing Scale

Declared values (must be multiples of 4) — unchanged project-wide scale, reused as-is:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge internal padding |
| sm | 8px | Compact stacks (status chip rows, form field gaps) |
| md | 16px | Default card padding, gap between stacked cards |
| lg | 24px | Section padding, dialog content padding |
| xl | 32px | Layout gaps between major page regions |
| 2xl | 48px | Major section breaks (rare on these screens) |
| 3xl | 64px | Page-level top offset (desktop admin only) |

Exceptions:
- **44px minimum touch target** on every interactive element in the employee camera flow
  (shutter button, retake/submit buttons, dismiss/"Đã hiểu" button) — already codified as the
  `mobile` (h-11, 44px) and `icon-mobile` (44×44px) `Button` size variants in
  `src/components/ui/button.tsx`. Nothing new to add.
- **72px shutter button** — the camera capture control itself is larger than the 44px floor
  (72px diameter circle) because it is the single most-tapped control on the highest-risk screen
  in the product (one-handed, gloved, poor light). This is a deliberate oversize exception, not
  a violation of the 8-point scale (72 = 8 × 9).
- The bottom nav (`--tf-bottomnav-h: 64px`) must never be covered by the camera sheet or any
  dialog — the camera sheet is a full-screen overlay that replaces the nav entirely while open
  (it is a modal task, not a nav destination), and closes back to the nav on exit.

## Typography

Reusing the existing type scale from `src/app/globals.css` — no new sizes introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 15px | 400 | 1.5 |
| Label | 13px | 500 | 1.4 |
| Heading | 16px | 500 | 1.4 |
| Display | 32px (mobile) / 44px (desktop) | 300 | 1.08 |

Notes:
- **Heading** maps to the existing `.heading-sm` class — used for card/section titles
  ("Ca làm hôm nay đã kết thúc", empty/error state titles, admin card headers). This phase does
  not introduce a new heading size.
- **Display** maps to the existing `.display-xl` class, reused unchanged for the live clock on
  the not-yet-checked-in state (already implemented in `attendance-status-card.tsx`) — this
  phase does not add a new numeric display treatment anywhere else. Do not use display size for
  distance numbers or coordinates; those are body/label size with `.num` (tabular figures).
- **Font weights used net-new by this phase: 400 (regular) and 500 (medium) only.** The 300
  (light) weight exists project-wide for `display-*`/`heading-lg`/`heading-md` and is reused
  as-is from existing layout chrome (`PageHeader`, page `<h1>`) — this phase does not author any
  new 300-weight text.
- All distances, coordinates, timestamps, and durations use the `.num` utility class
  (tabular figures) — existing convention, applies to the new distance/GPS copy in this phase.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--tf-canvas` `#ffffff` / `--tf-canvas-soft` `#f6f9fc` | Page backgrounds, admin table/card backgrounds |
| Secondary (30%) | `--tf-canvas` white surfaces bordered `--tf-hairline` (`.surface-card`, `.surface-panel`) | Cards, dialogs, table rows, employee bottom-sheet content |
| Accent (10%) | `--tf-primary` `#533afd` (indigo) | See "Accent reserved for" below — nothing else |
| Destructive | `--tf-error` `#b42318` | The three rejection banners; "Ngừng sử dụng điểm làm việc" confirm button only |
| Warning (load-bearing for D-20) | `--tf-warning` `#b54708` | The flagged-but-accepted "ngoài bán kính" banner; "cần xem lại" row highlight and badge in admin list — **never used for a true rejection, never used for a normal successful punch** |

**Accent reserved for, explicitly:**
1. The single filled-indigo primary CTA per screen/area:
   - Employee home: "Vào ca" / "Tan ca" (unchanged from current implementation)
   - Camera sheet, after photo captured: "Gửi chấm công" (submit)
   - Admin work-site screen: "Thêm điểm làm việc"
   - Admin record review dialog: "Đánh dấu đã xem xét"
2. Global focus ring (`:focus-visible`, existing rule, unchanged).
3. Active/selected nav item indicator (existing pattern, unchanged).

**Explicitly NOT accent-colored:**
- The camera shutter button is neutral (white/outline circular button per standard camera-UI
  convention), not filled indigo — it only *captures*, it does not *submit*. This keeps exactly
  one filled-indigo action per screen state and avoids the user reading the shutter as "the"
  primary action before a photo even exists.
- Status badges never use accent; they use the semantic tones only (success/warning/danger/info/
  neutral), per the existing `StatusBadge` component contract.

**Justified exception to the 60/30/10 surface rule:** the live camera viewfinder itself is not a
`--tf-canvas` surface — it is the device video feed. Chrome around it (shutter button, GPS status
chip, cancel button) sits on a `rgba(0,0,0,0.55)` translucent scrim over the video for legibility
against an arbitrary real-world background, not on a white/canvas surface. This is confined to
the camera sheet only; every other surface in this phase (admin screens, post-capture preview
chrome, all banners) follows the standard 60/30/10 tokens above. Gradient mesh (`--tf-mesh-*`)
is not used anywhere in this phase — reserved for login/onboarding per project rule.

| Empty state heading — needs-review list | "Không có bản ghi nào cần xem lại" |
| Empty state body — needs-review list | "Mọi lần chấm công gần đây đều nằm trong hoặc gần bán kính điểm làm việc." (reassuring, not alarming — this is a healthy-state empty list) |
| Error state — missing photo (server rejection) | Title "Thiếu ảnh chấm công" · body "Máy chủ từ chối vì không có ảnh đính kèm. Hãy chụp lại và gửi." |
| Error state — outside shift (server rejection) | Title "Ngoài giờ ca làm" · body "Bạn đang chấm công ngoài khung giờ ca được phân. Liên hệ quản lý nếu đây là nhầm lẫn." |
| Error state — network failure (server rejection) | Title "Mất kết nối mạng" · body "Không gửi được chấm công. Vui lòng kiểm tra mạng và chạm để gửi lại." (no auto-retry, no queued/"đang đồng bộ" language — per D-23) |
| Flagged-but-accepted (not error, not success) | Title "Đã ghi nhận — cách xa điểm làm việc" · body "Bạn cách {tên điểm làm việc} khoảng {khoảng cách}. Quản trị sẽ xem lại bản ghi này." · action "Đã hiểu" |
| Destructive confirmation — work site | "Ngừng sử dụng {tên điểm làm việc}?" → "Nhân viên chấm công sẽ không còn được tính khoảng cách theo điểm này nữa." · confirm label "Ngừng sử dụng" (tone: destructive, mirrors `ShiftsView`'s archive pattern — soft-delete via `is_active`, not hard delete) |

`review_status: pending|approved|rejected`) stay English per project convention.

## UI Considerations

Applicable state considerations resolved: 19 covered, 4 backstop, 3 unresolved

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| Screen — camera capture | Employee check-in/out | ✅ covered | Full-screen `Sheet` (not a routed page) opened from the existing "Vào ca"/"Tan ca" button; contains viewfinder → capture → preview → submit steps described below. No `<input type="file">` anywhere in this flow. |
| Screen — work-site declaration | Admin `/admin/work-sites` (new) | ✅ covered | Sibling of `ShiftsView`: `PageHeader` with count + "Thêm điểm làm việc", card grid (`ShiftCard`-equivalent `WorkSiteCard`), dialog form, archive via `ConfirmDialog`. Same skeleton/empty/error triad as `ShiftsView`. |
| Screen — attendance record review | Admin, opened from any attendance row | ✅ covered | `Dialog` (not a new route) showing captured photo (signed URL, `next/image` inside a fixed-aspect frame), distance-from-site, raw lat/lng (`.num`), "Mở trong Google Maps" external link, and review action buttons. |
| Screen — needs-review list | Admin `/admin/attendance/review` (new) or a filtered tab of the existing attendance screen (planner's call) | ✅ covered | `Table` layout: Nhân viên · Điểm làm việc · Khoảng cách (bold, warning-toned, includes multiplier e.g. "620m · gấp 6.2 lần bán kính") · Thời điểm · Trạng thái xem xét (`StatusBadge`) · Hành động ("Xem chi tiết" opens the review dialog above). |
| Rejection — missing photo | Camera sheet | ✅ covered | Primary defense is client-side: "Gửi chấm công" stays disabled until a photo exists (no error UI needed for the common path). Server-side rejection banner exists as defense-in-depth per D-20b: icon `CameraOff`, danger tone, copy in Copywriting Contract. Stays on the camera sheet, does not discard the frame if one exists client-side. |
| Rejection — outside shift | Camera sheet, after submit | ✅ covered | Icon `Clock`, danger tone, copy above. Includes a secondary link to "Bổ sung công" (`/employee/requests?type=attendance_supplement`, already exists) as the documented recovery path for a genuine mistake, not a retry of the same rejected punch. |
| Rejection — network failure | Camera sheet, after submit | ✅ covered | Icon `WifiOff`, danger tone. Explicitly: no spinner language implying queued/pending, no auto-retry timer. Button text is literally "Gửi lại" (send again), and the captured photo + acquired GPS fix are kept in memory so retry does not force a re-shoot — this reduces friction without reintroducing an offline queue (D-23 forbids persistence, not in-memory retry of the current attempt). |
| Rejection — visual distinguishability | All three above | ✅ covered | Same danger red family (consistent "this was rejected" signal) but distinct icon + distinct title + distinct body copy per D-20b — icon+text differentiation satisfies the project's "never color alone" accessibility rule while keeping one coherent "rejected" color language. |
| Flagged-but-accepted | Camera sheet, after submit | ✅ covered | Distinct warning-amber banner, own icon (`MapPinOff` or `AlertTriangle`, not the danger red icon), copy leads with "Đã ghi nhận" (recorded) before the caveat — reassurance first, per D-20's requirement to avoid panic. Requires an explicit acknowledgement tap ("Đã hiểu") rather than a transient toast, because a passing toast risks being ignored for information the employee needs to retain (unlike the plain success path, which uses the existing lightweight toast pattern). |
| Empty — work-site list | Admin | ✅ covered | See Copywriting Contract; visual pattern identical to `ShiftsView`'s `EmptyState` usage. |
| Empty — needs-review list | Admin | ✅ covered | See Copywriting Contract; framed as a healthy/reassuring empty state, not a "nothing here" dead end. |
| Empty — record has no photo | Admin review dialog | 🧪 backstop | Edge case for records created before this phase ships (no `attendance_photos` row) or a `check_out` without a paired photo if only one leg was captured. Show inline: "Bản ghi này không có ảnh đính kèm." in the photo slot instead of a broken image. No test evidence exists yet for this path — planner should add a fixture record without a photo. |
| Loading — admin lists | Work-site list, needs-review list | ✅ covered | Reuse `Skeleton` blocks exactly as `ShiftsView` does (`h-72 rounded-card` grid / table row skeletons) — zero new loading pattern. |
| Loading — signed photo URL | Admin review dialog | ✅ covered | Fixed-aspect placeholder box with `Skeleton` while the signed URL request resolves; on failure show inline "Không tải được ảnh — liên kết đã hết hạn." with a "Tải lại ảnh" retry button confined to the image slot (does not error the whole dialog). |
| Loading — camera opening | Employee sheet | ✅ covered | Between tap and live preview: black scrim with a centered "Đang mở camera…" label + spinner. This gap is called out by name in the research focus as the highest-risk transition on this screen; do not render a blank/frozen frame with no feedback during this window. |
| Loading — GPS acquisition | Employee sheet | ✅ covered | Small inline status chip near the submit button: "Đang lấy vị trí…" while pending, checkmark "Vị trí: đã xác định" once resolved. Submit stays disabled until resolved (see below) — this is a client-side gate, not a server rejection. |
| Loading — submit in flight | Employee sheet | ✅ covered | "Gửi chấm công" button shows spinner + "Đang gửi…", disabled, no double-submit possible — same disabled-during-pending convention already used by `handleCheckIn`/`handleCheckOut` in `employee-home-view.tsx`. |
| Permission-denied — camera | Employee sheet, `NotAllowedError` | ✅ covered | Full replacement of the viewfinder area (not a toast): icon `CameraOff`, "Không có quyền dùng camera", "TimeFlow cần quyền camera để chấm công. Vào cài đặt trình duyệt để cấp quyền, sau đó thử lại.", button "Thử lại" (re-invokes `getUserMedia`, since granting via browser settings often does not require a full page reload on mobile). |
| Permission-denied — location | Employee sheet, geolocation denied | ✅ covered | Same full-block pattern as camera permission-denied: icon `MapPinOff`, "Cần quyền truy cập vị trí", "TimeFlow cần vị trí để đối chiếu với điểm làm việc. Cấp quyền vị trí trong cài đặt trình duyệt rồi thử lại.", button "Thử lại". This is a **client-side pre-submit gate**, not one of the three D-20b server rejection reasons — it never reaches the server because no coordinate exists to send. Keeping it categorically separate from the three server reasons avoids inventing a fourth rejection reason, which D-20b does not authorize. |
| No-camera-device | Employee sheet, `NotFoundError`/`OverconstrainedError` | ⚠ unresolved | Same visual treatment as permission-denied (icon `CameraOff`, full block) is proposed, but there is **no fallback path** in this phase's scope — ATT-01 explicitly forbids a photo-library alternative, and no "office manual check-in" escape hatch exists in Phase 3. A device with genuinely no camera, or one where the browser cannot access it, cannot check in through this screen at all. This is a real dead end and is flagged here rather than silently designed around; planner/product should confirm this is accepted (likely yes, given the "no offline queue" precedent of accepting blunt failure over ambiguity) rather than assuming it. |
| Camera-in-use | Employee sheet, `NotReadableError` | 🧪 backstop | Distinct copy proposed ("Không mở được camera — có thể đang dùng ở nơi khác. Đóng ứng dụng khác rồi thử lại.") but this is a genuinely rare, hard-to-test browser condition; treat as a backstop state — implement the copy/branch but do not block phase completion on manufacturing this exact browser error in tests. |
| GPS acquisition timeout | Employee sheet | ⚠ unresolved | CONTEXT.md does not specify a timeout duration or the behavior when `getCurrentPosition` never resolves (common in poor-signal indoor environments — the exact gap `SUMMARY.md` flags for this phase). Recommend a 15-second timeout after which the GPS status chip switches to a retry affordance rather than blocking forever, but the number and exact fallback behavior need explicit confirmation at plan time, not silent invention here. |
| Device coverage for `getUserMedia()` | Employee sheet, all Android/iOS browsers in use by pilot companies | ⚠ unresolved | Named explicitly in `.planning/research/SUMMARY.md` §"Gaps to Address" as unresolved for this phase. This UI-SPEC designs for the documented `getUserMedia()` error taxonomy (`NotAllowedError`, `NotFoundError`, `NotReadableError`, `OverconstrainedError`) but cannot verify real device coverage among the pilot's actual employee phones from this research pass — carried forward as a known gap, not resolved here. |
| Mobile constraint — one-handed use | Camera sheet | ✅ covered | Shutter button and submit/retake buttons anchored to the bottom of the viewport within thumb reach; cancel/close control top-corner, small and secondary (not competing with the shutter). |
| Mobile constraint — bottom nav occlusion | Camera sheet | ✅ covered | See Spacing Scale exception — camera sheet fully replaces the nav while open rather than floating above/overlapping it. |
| Mobile constraint — status never color-only | All badges/banners in this phase | ✅ covered | Every rejection banner, the flagged-but-accepted banner, and every `StatusBadge` usage (including a new `review_status` mapping for the needs-review list) carries an icon + text label, per the existing project-wide rule — no new exception introduced. |
| Zero/one/many — needs-review list | Admin | ✅ covered | Zero → empty state above. One or many → same `Table` row template scales without a different layout; no special "exactly one result" treatment needed. |
| Long text — work-site name | Admin card, review dialog, needs-review table | 🧪 backstop | No character limit specified in CONTEXT.md for `work_sites.name`. Recommend `truncate` with a `title` attribute tooltip fallback in card/table contexts (existing project pattern for names elsewhere); treat as backstop pending a planner-set max length. |
